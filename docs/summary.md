# Serializer 프로젝트 정리: 문제, 해결, 개선 방향

근거와 수치의 출처는 [lab-notebook.md](lab-notebook.md)의 절 번호(§)로 적었다.

수치는 모두 직접 잰 값이다. 8~10절은 AWS VM 4대, 나머지는 로컬 PC(Ryzen 5 3600, 16 GB, Docker Desktop)에서 쟀다. 시뮬레이션이나 예상은 따로 표시했다.

> 최종 비교 수치는 abort 전송 경로를 고친 뒤 모든 주 실험을 다시 돌린 결과다(§39~§40, 83회).
> 클라우드 수치(8절)는 측정 도구(Caliper SDK) 부담을 고친 뒤 다시 잰 값이다(§68, §78, 90회).

## 1. 프로젝트 한눈에

- **무엇:** Hyperledger Fabric의 순서 결정(ordering)을 오더러 밖의 Kafka 프로세서로 빼낸다. 거기서 트랜잭션 충돌을 미리 풀어 사용자의 실패를 줄인다. 버린(abort) 기록은 별도 BFT 합의망(Watchdog: s-node, w-node)이 원장에 남긴다.
- **논문:** "Serializer: Transaction-Aware Byzantine Fault Tolerant Ordering Service for Fabric Blockchain" (IEEE Access 투고 원고).
- **구성 요소**
  - 수정된 Fabric 오더러: 배치를 Kafka로 보내고 결과 순서로 블록을 만든다.
  - Kafka 프로세서(Go, goka): ε-ordering 정렬, 사용자 통계(MongoDB), abort 통보.
  - s-node: 커미티 구성. Kubernetes에서 다중화했다.
  - w-node: abort 기록에 대한 BFT 합의와 원장.
  - 벤치마크: Hyperledger Caliper. 다중 사용자, 긴급 tx, Zipf 부하를 쓴다.
- **내가 한 일(요약)**
  - 시스템을 로컬에서 끝까지 돌게 만들었다.
  - 가용성·합의·스케줄링·지연 문제를 찾아 고쳤다.
  - 비교 대상(Fabric++, HTFabric)을 논문대로 구현해 같은 조건에서 비교하는 벤치마크를 만들었다.
  - 성능 차이의 원인을 구간 계측으로 찾아냈다.

## 2. 문제 → 원인 → 해결 → 결과

### 2.1 검증 노드(s-node)가 단일 장애점 (§1~§6)
- **문제:** s-node가 하나뿐이었다. 멈추면 커미티가 만들어지지 않아 전체가 멈춘다.
- **검토:** 세 구조를 비교했다.
  - ① 모든 pod가 동작하고 Kafka로 조율: 구현·검증 뒤 폐기했다. 검증 노드의 가용성이 Kafka에 묶이고 중계가 복잡해진다.
  - ② pod 간 libp2p 메시: 전환 순간 커미티가 중복될 수 있다.
  - ③ **Kubernetes Lease 기반 active-standby**: 채택했다.
- **해결**
  - Lease를 잡은 pod 하나만 libp2p를 연다. Service는 Ready 대신 pod 라벨로 활성 pod를 고른다. 롤링 업데이트와 PDB가 막히지 않게 하기 위해서다.
  - Lease를 잃은 pod는 스스로 종료해 w-node 연결을 끊는다.
  - 모든 pod가 같은 peer ID 키를 쓰고, 그 키 토픽은 만료 없음으로 설정했다.
  - w-node는 ping으로 끊김을 감지하고 재등록한다.
- **결과:** 활성 pod를 강제 종료하면 6.5초 뒤 다른 pod가 같은 peer ID로 이어받는다. 정상 종료면 0.5초다. w-node는 스스로 재접속해 새 커미티를 받는다.

### 2.2 합의되지 않은 데이터가 원장에 기록됨 (§11~§12)
- **문제:** w-node는 정족수에 못 미쳐도 블록을 기록했다. 실패한 데이터를 다시 시도할 방법도 없었다. s-node는 노드 하나로도 커미티를 만들어 혼자 정족수를 채울 수 있었다.
- **해결**
  - 정족수 미달이면 블록을 만들지 않는다.
  - 원장 블록에 Kafka abort 토픽의 반영 구간(파티션별 오프셋)을 적는다. 진행 위치를 원장이 기억하게 해서 노드별 상태가 필요 없다.
  - 밀린 기록은 최대 50개씩 묶어 한 블록으로 합의한다.
  - 실패하면 gossip으로 알리고 모두 다시 등록해 새 커미티로 재시도한다. 리더가 죽으면 벽시계 10초 단위로 정체를 감지해 다시 등록한다.
  - 커미티 최소 4명(f=1). 등록 요청은 30초가 지나면 버린다.
- **결과:** 팔로워·리더 장애, 멈췄던 리더의 복귀(이미 기록된 구간 제안 → 거절)에서도 원장에 중복이나 미합의 블록이 없다.
- **함께 찾은 것:** 같은 태그로 이미지를 다시 빌드하면 Kubernetes가 예전 이미지를 계속 쓴다. 그래서 "고친 코드가 실제로는 돌지 않았던" 실험이 있었다. 이후 매번 새 태그와 imageID를 확인한다.

### 2.3 원장의 사용자별 abort 횟수가 항상 비어 있음 (§13~§14)
- **원인:** 프로세서는 abort 기록에 Fabric Envelope을 넣는데, w-node는 다른 타입(`TransactionMsg`)으로 풀고 있었다. 사용자를 하나도 찾지 못했다. "MongoDB 연동 문제"라는 처음 가설을 데이터로 기각했다.
- **해결:** abort 기록에 사용자별 건수(`users`)를 싣고 w-node는 그 값을 더한다.

### 2.4 스케줄러가 사실상 무작위로 버리고, 필요 없는 abort를 냄 (§15~§16)
- **문제**
  - 실패 횟수를 읽기만 하고 쓰지 않았다. 희생자는 map 순회 순서로 정해졌다.
  - 쓰기–쓰기를 충돌로 봐서 불필요한 abort가 났다.
  - 풀리지 않은 tx는 조용히 사라졌다.
- **해결:** 읽기→쓰기 선후 관계만 충돌로 본다. 고리(SCC)에서만 버린다. 희생자는 사용자 실패율(보정한 비율) 기준으로 고른다.
- **결과(시뮬레이션):** 전체 실패율이 25.5% → 20.6%(배치 30), 이동이 많은 부하에서는 19.8% → 8.9%로 줄었다.

### 2.5 공정한 비교를 위한 기준 시스템 구현 (§19, §22, §29)
- **Fabric++**(SIGMOD'19)와 **HTFabric**(FGCS'22)의 정렬 알고리즘을 논문대로 구현했다. 같은 프로세서 자리에 끼워 같은 부하로 비교한다.
- **논문 오류 발견:** HTFabric 의사코드의 CalcDeg는 in/out-degree가 뒤바뀌어 있다. 정의(Definition 3.2, Fig. 4)를 따르고 그 사실을 기록했다.
- **Fabric++ 고리 열거 폭발:** 2000건 배치에 80초가 걸렸다. Johnson 알고리즘으로 바꿔 결과는 같게 유지하고 복잡도를 O((n+E)(C+1))로 맞췄다.
- **Serializer(논문 ε-ordering, Algorithm 1~4)** 구현
  - 논문 의사코드대로면 행렬의 위 삼각만 채워져 고리가 생길 수 없다. Figure 9에 맞게 해석했다.
  - 충돌 행렬을 인접 리스트로 바꿨다. 1080개 배치에서 결과가 완전히 같음을 테스트로 확인했다.
- **"논문 의미를 바꾸지 않는 개선만 적용"** 원칙을 세웠다. 논문과 달라지는 개선(SCC 분해, 긴급·일반 단일 그래프)은 별도 이름으로만 비교한다.

### 2.6 프로세서 경로가 느려 부하에서 지연이 3초까지 늘어남 (§18, §26)
- **원인(구간 계측)**
  - 배치 하나가 오더러 → Kafka → 프로세서 → Kafka → 오더러로 왕복한다. 오더러는 결과를 기다리는 동안 멈춘다.
  - 메시지가 들어갈 때 약 520 KB, 나올 때 약 570 KB였다(protobuf를 JSON base64로 감쌌다).
  - MongoDB `user`에 인덱스가 없어 upsert마다 전체를 훑었다.
  - Kafka를 한 번 더 거치는 Loopback이 있었다.
- **해결**
  - 결과는 envelope 대신 순서 인덱스만 보낸다(570 KB → 290 B).
  - 배치 ID로 짝을 맞춘다. 예전에는 commit 토픽의 다음 메시지를 무조건 받아 다른 배치로 블록을 만들 위험이 있었다.
  - incoming에 lz4 압축, Mongo 인덱스와 BulkWrite, Loopback 제거, sarama flush 1 ms를 적용했다.
- **결과(custom 부하):** 성공 TPS 34 → 96(약 2.8배), 커밋 지연 2.9 s → 0.7 s.

### 2.7 큰 abort 기록이 commit을 40 ms 늦춤 (§37~§38)
- **현상:** Serializer·Fabric++의 커밋 지연이 HTFabric보다 40~80 ms 길었다. 정렬 계산은 배치당 1 ms 미만이라 설명이 안 됐다.
- **분석**
  - 오더러 로그를 시각과 함께 남기도록 벤치를 고쳤다.
  - 프로세서 → Kafka → 오더러 → raft → 피어의 7개 구간을 블록 번호로 짝지어 배치 단위로 분해했다.
  - 차이는 "commit 보냄 → 오더러 수신"(9 ms 대 48 ms) 한 구간에만 있었다.
  - 이 지연은 버린 tx 수와 무관한 **고정 40 ms**였다. 크기 문제가 아니라 전송 방식 문제라는 뜻이다.
- **가설과 검증:** commit 바로 뒤에 같은 producer 연결로 나가는 큰 abort 기록이 원인이라고 봤다. 세 방식(같은 연결 / 다른 연결 / 100 ms 지연)으로 대조 실험을 했다.
  - 다른 연결만으로 48 → 7 ms가 됐다.
  - 지연 방식은 abort 통보를 늦추므로 다른 연결 방식을 기본값으로 정했다.
- **결과**
  - 같은 시간대 대조 실험에서 클라이언트 커밋 지연이 626 → 546 ms(−13%)로 줄었다. abort 통보 지연은 그대로였다.
  - 기본값을 바꾸고 83회를 다시 돌렸다. commit 구간은 모든 시스템에서 7~8 ms로 같아졌다.
  - Serializer의 커밋 지연이 HTFabric 이하로 내려왔다. smallbank에서 563 대 570~602 ms다.
  - 성공 처리량도 올랐다. 예: custom+Query ε 1/1, 긴급 1에서 138 → 149/s.

### 2.8 버려진 트랜잭션을 클라이언트가 10초 뒤에야 앎 (§17, §22)
- **문제:** 프로세서가 버린 tx는 블록에 들어가지 않는다. 클라이언트는 커밋 대기 시간(10 s)을 다 기다린 뒤 실패로 알았다.
- **해결:** abort 기록에 tx ID와 요청 인자를 싣는다. 클라이언트(Caliper 워크로드)는 abort 토픽을 구독해 바로 실패로 끝낸다. goka의 Snappy 압축 때문에 kafkajs-snappy가 필요했다.
- **결과:** 버려진 tx의 실패 통보가 10 s → 약 0.5 s.

### 2.9 벤치마크 인프라 (§17, §20, §25, §35)
- **Caliper 다중 사용자 워크로드:** 사용자 5명, 사용자별 네트워크 지연, VIP 긴급 tx, Zipf 계좌, smallbank·custom 부하, 읽기 전용 비율.
- **보조 부하(custom):** Fabric 성공률을 주 부하와 같은 수준(약 35%)으로 맞췄다. "부하가 너무 세서 모든 알고리즘이 나빠 보이는" 문제를 피하려는 것이다.
- **집계 도구**
  - 사용자별 성공·공정성(표준편차)
  - 긴급 성공률
  - 실패 경로별 지연(abort 통보 / 피어 무효 / 시간 초과)
  - tx 종류별 지연
  - 커밋 경로 구간 분해(`aggregate-path.js`)
- **포화 실험:** 이 PC의 상한은 약 350~440 TPS이고 병목은 호스트 CPU다. 1000 TPS 이상은 클라우드가 필요하다는 근거가 됐다.

### 2.10 외부 정렬 경로의 진짜 비용: 메시지 크기가 아니라 측정 환경 (§44~§46)
- **현상:** 부하가 오를수록 외부 정렬의 추가 지연이 커졌다(400 TPS에서 +85~105 ms, Serializer가 380 TPS밖에 못 받음). 배치 하나가 Kafka를 왕복하는 70~87 ms 중 약 70%가 "배치(약 520 KB)를 프로세서로 보내는" 구간이었다.
- **처음 가설과 검증:** "메시지가 커서"라고 보고, envelope 대신 메타데이터만 보내면 50 → 5~10 ms가 될 것으로 추정했다. **구현 전에 실제 배치로 측정했다.**
  - 같은 525 KB를 Docker 내부망으로 보내면 매번 약 3 ms였다.
  - 지금 경로(Docker Desktop의 `host.docker.internal` 포트 전달)로 보내면 6 ms와 45~50 ms로 갈렸다.
  - **원인은 크기가 아니라 측정 환경의 포트 전달 프록시**였다. 첫 추정이 틀렸음을 데이터로 확인하고 정정했다.
  - 이 비용은 Kafka를 거치는 시스템에만 붙어, 비교를 Fabric 쪽에 유리하게 왜곡하고 있었다.
- **해결 (AWS 분산 배포까지 고려)**
  - ① Kafka 주소를 코드 상수에서 설정으로 바꾸고(`KAFKA_BROKERS`, `-brokers`) 내부망으로 연결했다.
  - ② 오더러가 tx별 메타데이터(키·버전·사용자·긴급)만 보낸다. 배치 1000~5000에서는 메시지가 10분의 1 이하가 되어 배치당 30~150 ms를 줄인다(실측).
  - 블록 생성 경로는 건드리지 않았고, 예전 형식도 계속 받는다.
- **결과**
  - 배치 메시지 523 → 32 KB, 외부 정렬 왕복 약 70 → 16 ms.
  - 커밋 지연 547 → 485 ms, abort 통보 520 → 410 ms(같은 조건 1회).

### 2.11 검증 노드 장애 복구 시간(MTTR) 절반 이하로 (§48~§49)
- **정의를 먼저 정했다:** MTTR = 장애 발생부터 **모든 w-node가 새 커미티를 받아 합의를 다시 할 수 있을 때까지**. 업계의 "Mean Time To Recovery/Restore"와 같은 정의다. 논문의 350 ms는 시뮬레이션(Fig 15)에 넣은 설정값이라, 실제 구조에서 이 정의로 측정했다.
- **측정으로 찾은 병목** (w-node 10개, 장애 유형별 반복, dry run 6번)
  1. Lease 만료 6초.
  2. w-node 감지·재접속 3~5초.
  3. **libp2p dial backoff:** 다이얼이 한 번 실패하면 약 5초 동안 그 peer로 다이얼하지 않아, 1초마다 재시도해도 소용이 없었다.
  4. 커미티 대기 3초.
  5. 활성 직후 일찍 만든 커미티가 갈라짐.
  6. 늦게 붙은 노드가 혼자 남음.
- **해결**
  - Lease 2초.
  - w-node 확인·재접속 1초.
  - 재접속 전에 주소록과 dial backoff를 지운다.
  - 연결된 w-node가 모두 등록하면 커미티를 즉시 만든다(활성 직후 3초 유예).
  - 늦게 온 노드는 방금 커미티와 합친다.
- **결과 (중앙값, 각 10회)**
  - 멈춤 장애 11.8 → **5.4 s**, 강제 종료 10.8 → **5.4 s**. 흔들림도 최대 12.7 → 6.3 s로 줄었다.
  - 10분 무장애 관찰과 1시간 37분 벤치마크 부하 동안 잘못된 전환 0회.
- **위험한 개선은 측정 후 기각했다**
  - Lease 1초로는 2.9~3.5 s까지 줄었다.
  - 그러나 PC가 바쁠 때 잘못된 활성 전환과 pod 재시작이 생겨 채택하지 않았다.
  - 무상태 커미티(≈1 s)는 악의적인 w-node의 목록 조작을 막는 검증이 따로 필요해 보류했다.

### 2.12 1,000 TPS를 위한 분산 배포 준비 (§51~§52)
- **CPU 몫 측정(400 TPS):** 클라이언트(Caliper) 41~55%, 피어 18~27%, Serializer의 w-node 합의 28%.
  - 클라이언트만 밖으로 빼도 약 600~700 TPS가 한계라는 근거를 얻었다.
- **배포 도구:** VM 4대(클라이언트, Fabric, Kafka, Watchdog) 구성의 설정 파일 하나와 역할별 설치 스크립트를 만들었다.
  - 실험 스크립트는 그대로 두고 Docker over SSH로 다른 VM을 다룬다.
  - 로컬 동작이 바뀌지 않음을 확인했다.

### 2.13 측정 도구가 Serializer에만 부담을 줌 (§68, §78)
- **문제:** 클라우드 1,000 TPS에서 Serializer만 보낸 TPS가 867~986에 그쳤다. 커밋 지연과 블록 간격도 Fabric보다 길게 나왔다.
- **원인 찾기**
  - 오더러 계측(§67): run loop가 1초 중 약 900 ms를 "받을 수 있는데 빈" 상태로 보냈다. → 오더러는 병목이 아니고 tx가 덜 들어온다.
  - 커밋 대기를 줄이거나 abort 통보를 꺼도 그대로였다. Caliper 워커 CPU는 BE에서 100~120%로 포화됐다.
  - CPU 프로파일과 SDK 계측: 워커당 tx 리스너가 BE에서 약 2,150개, A1에서 약 90개였다.
  - 원인: 프로세서가 버린 tx는 블록에 나오지 않아 커밋 리스너가 시간 초과까지 남는다. fabric-common 2.2.20은 블록의 tx마다 모든 리스너를 훑고, 맞지 않을 때마다 디버그 로그를 부른다.
- **해결:** 워크로드에서 맞는 리스너만 원래 함수로 넘긴다(`installFastTxListener`, 동작은 같다). 첫 시도의 해제 표 버그(30초 시간 초과)도 찾아 고쳤다.
- **결과**
  - Serializer가 1,000 TPS를 다 보낸다(999~1,001). Fabric 수치는 1~2% 안으로 그대로였다.
  - 90회를 다시 쟀다. 성공 배율이 ×1.21~2.54에서 ×1.31~2.98로 커졌고, "지연 손해"로 보였던 것이 사라졌다(커밋 지연 −11~−187 ms).

### 2.14 고부하에서 무엇이 먼저 무너지는가 (§69~§71, §80)
- **문제:** 2,000~5,000 TPS에서 Serializer가 버티는지 보고 싶었다.
- **진행**
  - 첫 시도는 보낸 TPS가 약 1,220과 2,100~2,250에서 멈췄다. 설정 파일의 `WORKERS=5`가 환경 변수를 덮어쓴 버그와, 클라이언트 VM CPU 포화(약 90%) 때문이었다. 버그를 고치고 클라이언트를 32 vCPU로 키웠다.
  - 정상 범위는 배치 100에서 약 2,000 TPS(성공 496/s, 280 ms), 배치 1000에서 약 3,000 TPS(925/s, 674 ms)였다. 그 위에서는 커밋 지연이 7~25 s로 밀리며 무너졌다.
  - 컨테이너별 CPU를 재 보니 포화는 피어 두 개였다(합계 약 11코어, Fabric VM 89~95%). 정렬 경로(오더러·Kafka·프로세서)는 보낸 만큼 받았다(Kafka 왕복 7~17 ms).
- **결과:** 4,000 TPS·배치 5000에서 Serializer는 성공 643/s(지연 4.4 s), Fabric은 14/s(20.7 s)였다. 피어가 포화돼도 Serializer는 블록이 작아(2,525 대 4,753 tx) 더 버틴다. 4,000 TPS를 정상으로 처리하려면 배치보다 피어 CPU(Fabric VM 확대나 피어 분산)가 먼저다.

## 3. 실험으로 알게 된 것

1. **"블록 안에서 잘 푸는 것"과 "끝단 성공"은 다르다 (§32)**
   - 블록 안만 보면 Serializer(ε 1/1)가 HTFabric(WARD)보다 많이 살린다(85% 대 75%). 실제 스택(custom)에서는 WARD가 앞서거나 같은 수준이었다(지연 수정 전 −5%, 수정 후 비슷).
   - 원인: 블록 안에서 많이 살릴수록 인기 키에 쓰는 tx를 더 많이 커밋한다(배치당 59 대 43). 그만큼 다음 블록들을 기다리던 tx가 낡은 읽기가 된다.
   - WARD는 인기 키 쓰기를 블록 뒤로 보내 스스로 무효가 되게 한다. 그래서 배치 사이의 손해가 적다.
2. **읽기 전용 우선의 효과와 한계 (§33~§34, §36)**
   - 읽기 전용을 블록 맨 앞에 두면 같은 블록 안에서는 무효가 0이다. smallbank에서 Query 성공률은 Fabric 38%, WARD 59%, Serializer 66%였다.
   - 남은 34%는 이전 블록 때문이다. 상태 없는 프로세서로는 막을 수 없음을 Zipf 모델로 정량 확인했다.
3. **긴급 우선 구조의 비용 (§32~§33)**
   - 긴급 그룹 전체를 앞에 두면, 긴급 tx가 쓴 키를 읽는 일반 tx는 그래프에 들어가기 전에 버려진다. 블록 안 성공이 85% → 65%로 떨어진다.
   - 논문 ε 값(긴급 0.1)에서는 긴급 tx의 90%가 그래프 없이 처리돼 긴급 우선 효과도 약해진다.
4. **피어 무효 실패는 성공보다 늦게 통보된다 (§35)**
   - 오래 기다린 tx일수록 그 사이 커밋된 블록이 많아 낡기 쉽다. 측정값을 그대로 읽으면 생기는 오해(선택 편향)를 짚었다.
   - 같은 편향 때문에 "성공한 tx의 커밋 지연"만 보면 성공을 더 많이 살리는 시스템이 불리하게 보인다. 배치 100, 350 TPS에서 커밋 지연은 Serializer +22 ms였지만, 모든 tx가 결과를 받기까지의 평균은 −24 ms였다(§50). 지연은 두 지표를 함께 보고한다.
5. **측정 범위를 넓혀 다시 쟀다 (§41~§44)**
   - 논문 A-1은 "s > 1.15부터 제안 시스템이 앞선다"고 했다. 250 TPS에서 s 0~2를 촘촘히 재 보니 **역전 지점이 없었다.** 균등 분포(s 0)에서도 +9~11%였다. 계좌 100개면 균등이어도 Fabric 성공률이 60%일 만큼 충돌이 많기 때문이다.
   - 추가 지연은 고정값(논문 +50 ms)이 아니라 **부하의 함수**였다. 배치가 차는 동안 왕복이 가려지므로 200 TPS 이하에서는 +20~50 ms, 300 TPS 이상에서는 +40~90 ms였다.
   - 실험 도중 PC 성능 저하가 부하 효과와 섞인 것을 발견했다(같은 조건에서 지연 +0.15~0.4 s). 부하 순서를 섞고 기준점을 반복해 다시 쟀다.
6. **배치를 키우면 기존 Fabric은 무너지고, 제안 시스템은 버틴다 (§50)**
   - 배치 100 → 1000에서 Fabric 성공률은 36% → 16%로 떨어진다. Serializer는 약 50%를 지킨다. 성공 처리량 차이는 1.4배 → 3.4배가 된다.
   - 읽기 성공률은 오히려 오른다(71% → 92%). 읽기를 블록 앞에 두므로 같은 블록의 쓰기에 영향받지 않고, 블록 수가 줄어 배치 사이에 낡는 일도 준다.
   - 사용자 간 공정성도 좋아진다. 표준편차가 3.7 → 0.5로 준다. 네트워크 지연 차이가 배치 대기에 묻히기 때문이다.
   - 대가: 배치 대기로 지연이 수 초가 되고(배치 1000에서 약 2.5~3.4 s), abort 통보도 늦어진다.

## 4. 시스템별 문제점과 개선 방향

### Fabric (기준)
- **문제:** 순서를 도착순으로 정한다. 배치 안의 읽기–쓰기 충돌이 그대로 피어에서 무효가 된다(custom에서 블록 안 성공 48%).
- **개선 방향:** 재정렬(Fabric++, HTFabric, Serializer)이 이것을 다룬다.

### Fabric++
- **문제**
  - 고리를 모두 열거하므로 배치가 크면 시간이 폭발한다(Johnson으로도 고리 수에 비례).
  - 블록 안에서는 가장 많이 살리지만(90%), 인기 키 쓰기를 가장 많이 커밋해 배치 사이 손해가 크다.
  - 조기 abort는 논문 문구("뒤에 온 것을 버린다")와 실제로 낡은 쪽이 다를 수 있다.
- **개선 방향:** 고리 열거 대신 SCC 단위 처리. 희생자 선택에 "인기 키 쓰기" 비용을 반영.

### HTFabric (WARD만, 재실행 제외)
- **문제**
  - 충돌을 풀지 않고 피어로 넘긴다(블록 안 무효 25%). 실패를 빨리 알려 주지 못한다(abort 통보 없음).
  - 공정성이 가장 나쁘다(사용자 간 표준편차 최대).
  - 재실행까지 넣으면 성공은 약 2배로 예상되지만(측정 아님), 보증을 우회하고 사용자가 승인한 결과와 달라질 수 있다.
- **개선 방향:** 재실행은 정렬과 별개 기법이다. Serializer 블록에도 붙일 수 있으므로 따로 평가해야 한다.

### Serializer (논문 ε-ordering)
- **문제**
  1. 상태가 없어 배치 사이의 낡은 읽기를 미리 걸러내지 못한다. 실패의 대부분이 여기서 나온다.
  2. 긴급 그룹을 먼저 두는 구조 때문에 일반 tx가 손해를 본다.
  3. 논문 ε 값(0.1/0.75)은 부하에 따라 맞지 않는다. custom에서는 ε 1/1이 14% 높았다.
  4. 인기 키 쓰기를 많이 커밋해 다음 블록들을 망가뜨린다.
  5. ~~abort 기록이 버린 tx의 envelope 전체를 담아 크다~~ → 해결했다. 전송 경로는 §38, 크기는 §46(프로세서가 envelope 대신 메타데이터를 받으므로 abort 기록에 envelope이 없다).
- **개선 방향**
  - **상태 S 도입(논문 Algorithm 1 3행의 원래 의도).** 프로세서가 내보낸 순서로 키별 마지막 쓰기 버전을 유지한다. tx의 읽기 버전(`ReadVers`)과 비교해 낡은 tx를 그래프 전에 버리고 즉시 통보한다. 대가는 재시작·파티션 이동 시 상태 복구다.
  - 무상태 대안: 같은 배치에서 더 새 버전을 읽은 tx가 있으면 낮은 쪽을 버린다(Fabric++ 조기 abort 방식). 일부만 잡는다.
  - 희생자 동점 규칙에 "인기 키에 쓰는 tx(배치 안 out-degree 큰 것) 우선"을 넣는다. 논문의 abort 점수 f(n)은 바꾸지 않는다.
  - 긴급·일반을 한 그래프에서 처리하되 긴급에 가중치를 둔다(논문과 달라지므로 별도 이름).
  - 부하에 따라 ε를 고르는 기준을 둔다(그래프 크기·충돌 밀도 기반). §73~§77에서 근거를 얻었다: 배치가 작고 부하가 여유로우면 큰 ε, 배치가 크거나 피어 한계에 가까우면 작은 ε(10절). 정렬 시간 예산과 피어 부하에 맞춘 자동 조절이 다음 후보다.
  - abort 기록에서 envelope을 빼고 tx ID와 사용자만 싣는다(w-node가 쓰는 정보만).

### 시스템 공통 (오더러·인프라)
- **문제**
  - 오더러가 배치 하나씩 보내고 결과를 기다린다(lock-step).
    - 예전 경로에서는 한 바퀴 70~87 ms라 처리 상한이 약 500~650 TPS로 예상됐다(§28).
    - §46 이후에는 약 16 ms라 배치 100 기준 계산상 수천 TPS다. 이제 병목은 PC CPU(보증·검증·클라이언트)다(§51).
  - 커밋 지연의 가장 큰 몫은 배치가 차기를 기다리는 시간(약 200 ms)이다.
  - 검증 노드(s-node) 장애 MTTR은 지금 구조와 안전한 설정으로 약 5초다(Lease 만료 + 재접속 + 커미티 생성). 더 줄이려면 대기 pod가 등록을 복제하거나(약 3초), 목록 검증을 갖춘 무상태 커미티가 필요하다.
  - commit 토픽 이름과 consumer group이 고정이다. 오더러나 채널이 여럿이면 깨진다.
  - 프로세서가 응답하지 않으면 오더러가 무한정 멈춘다.
- **개선 방향**
  - 배치 ID 기반으로 여러 배치를 동시에 처리(파이프라이닝)한다.
  - 오더러에 타임아웃을 두고 프로세서가 응답하지 않으면 도착순으로 대체한다.
  - 채널별 토픽과 consumer group을 쓴다.
  - ~~클라우드에서 1000 TPS 이상 실험을 한다.~~ → 했다(8~9절). 이 구성(Fabric VM 16 vCPU)의 한계는 피어 CPU다. 배치 100에서 약 2,000 TPS, 배치 1000에서 약 3,000 TPS를 넘으면 무너진다. 다음은 Fabric VM 확대, 피어 분산, 이벤트 구독 분산이다(§80).

**한 줄 요약**

- **보조 부하(custom):** ε를 1에 가깝게 두면 HTFabric과 같은 수준이다. 긴급 tx 성공률은 가장 높다. 논문의 ε 값은 이 부하에 맞지 않아, ε를 부하에 맞춰 골라야 한다.
- **공정성:** Fabric++가 가장 좋다. Serializer는 그다음 수준이다.
- **abort 통보:** 프로세서가 버린 tx는 0.4~0.57 s 안에 클라이언트에 알려진다. 이전에는 10 s를 기다렸다.

**측정의 한계 (밝혀 둘 것)**
- 단일 PC(약 350~440 TPS 상한)에서 쟀다.
- 실행 묶음 사이에 ±4% 정도의 환경 흔들림이 있다. 그래서 비교는 같은 묶음 안에서만 한다.
- HTFabric은 재실행(TSP)을 빼고 정렬(WARD)만 비교했다.

## 10. ε의 비용과 이득 (§73~§77)

[experiments/02-epsilon-realtime/METRICS.md](../experiments/02-epsilon-realtime/METRICS.md)에 지표 정의와 그림(P1~P5)이 있다. Fabric 비교가 아니라 정렬 시스템 자체의 동작을 보인다.

**방법:** 실험 부하와 같은 모양의 합성 배치를 실제 정렬 코드(`scheduleEpsilon`)로 정렬해 시간을 재고, 도착 → 배치 → 정렬 흐름을 계산했다(시뮬레이션). 클라우드에서 몇 점을 실측해 맞는지 확인했다(§77).

**정렬 비용** (smallbank 배치 10000, 긴급 없음, ms 중앙값)

| ε | s 1.0 | s 2.0 |
|---|---|---|
| 0 | 0.6 | 0.4 |
| 0.5 | 48 | 401 |
| 0.1/0.75 (원 실험 값) | 136 | 1,545 |
| 1 | 263 | 2,128 (최대 5,623) |

**이득** (custom, 인기 키 0.2/0.1)

| 배치 | 살린 비율 ε 0 → 1 | 따라갈 수 있는 TPS ε 0 → 1 (최악) |
|---|---|---|
| 1,000 | 44.5% → 79.8% | 33k → 28k (27k) |
| 10,000 | 13.8% → 18.6% | 47k → 9.2k (2.9k) |

**클라우드 확인** (custom, 3회)
- 배치 1000, 1,000 TPS: ε 1이 ε 0보다 성공 +51%(469 대 311/s), 지연은 비슷하다.
- 배치 1000, 3,000 TPS: ε 1은 블록당 유효 tx가 1.8배라 피어 커밋이 밀려(지연 11.8 s) 성공이 ε 0의 1/4이다(148 대 641/s).
- 배치 10000, 2,000 TPS: ε 1의 정렬이 평균 547 ms(최대 1.2 s)라 지연이 4.4 → 6.0 s로 늘었다.
- 배치 안 살린 비율은 시뮬레이션과 0.5%p 안에서 같았다.

**판단**
- ε는 정렬 계산 비용의 상한을 정하는 손잡이다. 배치 10000에서 ε ≤ 0.5는 20k TPS까지 1 s 마감을 지키고, ε 1은 10k TPS에서 배치의 67%가 마감을 넘는다(시뮬레이션).
- ε의 비용은 정렬 시간만이 아니다. 더 많이 살린 tx를 피어가 커밋하는 부담도 있다.
- 그래서 부하가 여유롭고 배치가 작으면 큰 ε, 배치가 크거나 피어 한계에 가까우면 작은 ε를 쓴다.
- 긴급 tx: ε_urgent를 키우면 긴급 생존율이 74%에서 99.7%로 오른다(배치 1000). 비용은 31 ms 이하다. 원 실험 값(긴급 0.1)은 ε 0과 비슷한 수준이다.
- smallbank(키 200개)에서는 ε를 키워도 살리는 tx가 늘지 않는다. 이 부하에서 Fabric 대비 이득은 주로 읽기 전용을 앞에 두고 충돌할 tx를 블록에서 빼는 데서 나온다(§73).
