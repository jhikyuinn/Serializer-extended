# weave-kafka
Kafka for Weave

Fabric 오더러가 보낸 배치를 받아 트랜잭션 순서를 정하는 Kafka 프로세서다(`processor/processor.go`).

```
오더러 → mychannel-incoming → 프로세서 → mychannel-commit → 오더러 (블록 생성)
                                       └→ mychannel-abort  → w-node (합의 후 감사 원장에 기록)
```

## 실행

```bash
docker compose -f docker-compose.yml -f docker-compose.processor.yml up -d          # Kafka + 프로세서 + MongoDB
docker compose -f docker-compose.yml -f docker-compose.processor.yml up -d --build processor   # 코드를 고친 뒤
```

## 트랜잭션 스케줄링

### 핵심 고려사항

- **목적은 사용자 만족도다.** 프로세서는 사용자의 트랜잭션 실패를 줄이기 위해 있다. 전체 실패율을 낮추는 것과, 실패가 특정 사용자에게 몰리지 않게 하는 것 둘 다 필요하다.
- **실패 "개수"만으로는 만족도를 말하기 어렵다.** 1000건 중 10건 실패한 사용자가 2건 중 2건 실패한 사용자보다 더 보호받게 된다. 그래서 판단 기준은 실패율(실패/제출)로 한다.
- **긴급 우선 처리는 전체 실패율을 줄이지 않는다.** 실패를 긴급에서 일반으로 옮길 뿐이다. 전체 실패율은 순서 재배치와 "꼭 필요한 것만 버리기"에서 줄어든다. 긴급 우선은 그 위에 얹는 정책이다.
- **긴급과 일반을 가리지 않고 abort를 모두 센다.** 사용자별로 지금까지 거절된 트랜잭션 수를 저장한다.

### 이전 동작의 문제

| 문제 | 내용 |
|---|---|
| 실패 횟수가 쓰이지 않음 | MongoDB에서 읽어 출력만 했다. 횟수로 정렬하는 함수는 호출되지 않았다. |
| abort 대상이 사실상 무작위 | 순서를 정할 수 없으면 map에서 처음 나온 트랜잭션을 버렸다. 충돌 고리에 속하지 않은 것이 뽑힐 수도 있었다. |
| 불필요한 abort | 같은 키를 쓰는 트랜잭션 둘이 한 배치에 있으면 하나는 반드시 버려졌다. Fabric에서는 쓰기만 겹치는 것은 충돌이 아니다. |
| 일반 트랜잭션에 불리 | 커밋된 긴급과 키가 겹치는 일반 트랜잭션은 순서를 바꿔 볼 것도 없이 바로 버려졌다. |
| 일반 abort 미집계 | MongoDB에는 긴급 트랜잭션의 abort만 쌓였다. |

### 개선사항

**1. 꼭 필요한 것만 버린다.**
Fabric은 블록 안에서 앞선 트랜잭션이 쓴 키를 뒤의 트랜잭션이 읽었으면 뒤의 것을 무효로 한다. 그래서 "A가 읽은 키를 B가 쓴다"면 A를 B보다 앞에 두면 된다. 이 선후 관계가 고리를 이룰 때만 하나를 버리고, 나머지는 순서만 맞춰 모두 커밋한다. 쓰기만 겹치는 것은 충돌로 보지 않는다.

**2. 고리에서 버릴 트랜잭션을 정해진 기준으로 고른다.** 위에서부터 차례로 적용한다.

| 순서 | 기준 | 이유 |
|---|---|---|
| 1 | 긴급이 아닌 것 | 긴급 트랜잭션을 보호한다 |
| 2 | 고리를 더 많이 끊는 것 | 전체 abort 수를 줄인다 |
| 3 | 실패율이 낮은 사용자의 것 | 실패가 한 사용자에게 몰리지 않게 한다 |
| 4 | 늦게 들어온 것 | 결과가 매번 같도록 한다 |

실패율은 `(실패+1)/(제출+2)`로 계산한다. 제출이 적은 사용자의 값이 한두 건으로 크게 흔들리지 않게 하기 위해서다. 3번은 어차피 하나를 버려야 하는 자리에서만 쓰이므로 전체 실패율을 해치지 않는다.

**3. 남은 트랜잭션은 선후 관계를 지키면서 긴급을 앞에 둔다.** 그다음은 들어온 순서다. 읽기만 하는 트랜잭션도 같은 방식으로 자리를 정한다(자기가 읽은 키를 쓰는 트랜잭션보다 앞).

**4. 사용자별 제출·실패 건수를 누적한다.** MongoDB `User.abortTransaction`:

```json
{ "user": "User51", "submitCount": 4, "abortCount": 2 }
```

- 쓰기가 있는 트랜잭션만 센다. 읽기만 하는 트랜잭션은 버려질 일이 없다.
- 사용자는 체인코드가 처음 건드린 키로 본다(기존 방식 그대로).
- MongoDB를 읽지 못해도 순서 결정은 멈추지 않는다. 그 배치에서 3번 기준만 빠진다.

**5. abort 기록에 사용자별 건수를 싣는다.** `mychannel-abort`의 기록에 `users`가 들어가고, w-node는 이 값을 감사 원장 블록(`NumofAbortTransaction`)에 적는다.

```json
{ "timestamp": 1791727104375, "data": [ ...abort된 Envelope... ], "users": { "User60": 1 } }
```

### 확인한 동작

모든 블록에서 커밋된 트랜잭션은 피어의 유효성 플래그가 전부 VALID였다(블록 37~46).

| 배치 | 이전 | 지금 |
|---|---|---|
| `./network.sh load` 5건 (같은 사용자에 대한 쓰기가 겹침) | 2건 abort | 0건 abort, 5건 커밋 |
| 같은 키를 읽고 쓰는 1건 + 쓰기만 하는 2건 | 최소 1건 abort | 0건 abort, 읽는 것이 앞에 놓임 |
| 일반 사용자 둘의 맞물린 송금(User51↔User52), 4회 반복 | 무작위 | 매번 1건 abort. 대상이 User52 → User51 → User51 → User52로 돌아가 둘 다 4건 중 2건 |
| 긴급 2건 + 일반 1건이 한 고리, 2회 | 무작위 | 두 번 모두 일반 1건만 abort (일반이 먼저 도착했고 실패율이 더 높았을 때도) |

### 알아둘 점과 남은 것

- **긴급 판정이 넓다.** 트랜잭션이 쓰는 값 중 하나라도 `UserInfo.Urgency`가 참이면 긴급으로 본다. 그래서 일반 사용자가 VIP에게 보내는 송금도 긴급이 된다. 기존 방식 그대로이며 바꾸지 않았다.
- **긴급 보호는 전체 abort 수를 늘릴 수 있다.** 긴급 한 건을 버리면 풀릴 고리를 일반 여러 건을 버려서 푸는 경우가 있다. 기준 1과 2의 순서를 바꾸면 반대가 된다.
- **쓰기만 겹치면 블록에서 뒤에 놓인 것이 최종 값이 된다.** Fabric의 동작과 같다. 앞의 쓰기는 커밋되지만 값은 덮어써진다.
- **실패율은 전체 기간의 누적이다.** 최근 실패에 더 무게를 두거나 연속 실패를 따로 보지는 않는다.
- **버려진 트랜잭션은 다시 넣지 않는다.** 클라이언트가 다시 제출해야 하고, 다시 제출한 것은 새 제출로 센다.
- **제출 건수를 세기 전의 기록**(`submitCount`가 없는 문서)은 실패 건수만큼은 제출한 것으로 보고 계산한다.
- **성능 수치는 다시 재지 않았다.** 위 확인은 동작 확인이다. 충돌 비율과 사용자 분포를 바꿔 가며 전체 실패율, 긴급 실패율, 사용자별 실패율 분포를 기존 Fabric과 비교하는 실험이 남아 있다.
- 프로세서가 죽으면 오더러가 멈추는 문제, 한 건짜리 배치는 abort 기록을 남기지 않는 동작은 그대로다.

### 기존 Fabric과의 비교 (시뮬레이션)

`processor/scheduler_test.go`는 같은 배치를 두 방식으로 처리해 비교한다. 기존 Fabric은 도착 순서 그대로 두고 검증 규칙(앞선 유효 트랜잭션이 쓴 키를 읽었으면 무효)을 적용한 것이다. 스케줄러가 낸 순서가 그 검증을 전부 통과하는지도 함께 확인한다.

```bash
docker run --rm -v "$PWD:/src" -w /src golang:1.24-bookworm \
  go test -mod=vendor -count=1 -v ./processor/processor.go ./processor/scheduler_test.go
```

사용자 100명(10명이 VIP), 제출 빈도는 사용자마다 다름, 배치 2000개 기준 결과다.

| 작업 구성 | 배치 크기 | 전체 실패율 (Fabric → 스케줄러) | 긴급 실패율 | 일반 실패율 | 스케줄링 시간 |
|---|---|---|---|---|---|
| 자기 계좌 위주 | 10 | 10.96% → 8.34% | 16.76% → 11.95% | 9.45% → 7.40% | 10µs |
| 자기 계좌 위주 | 30 | 25.45% → 20.61% | 36.62% → 28.53% | 22.51% → 18.52% | 36µs |
| 자기 계좌 위주 | 100 | 46.03% → 40.20% | 58.57% → 48.91% | 42.75% → 37.92% | 211µs |
| 계좌 간 이동 40% | 10 | 7.63% → 3.00% | 10.69% → 4.45% | 6.89% → 2.65% | 7µs |
| 계좌 간 이동 40% | 30 | 19.83% → 8.94% | 26.97% → 13.27% | 18.07% → 7.87% | 27µs |
| 계좌 간 이동 40% | 100 | 38.11% → 19.62% | 46.82% → 26.38% | 35.98% → 17.97% | 154µs |

- **확인된 것:** 전체 실패율이 모든 경우에 낮아진다. 한 사용자가 자기 계좌를 연달아 읽고 쓰는 충돌은 누구도 풀 수 없어서, 서로 다른 계좌가 얽히는 작업일수록 효과가 크다.
- **확인되지 않은 것 (긴급 우선):** 긴급 실패율이 일반보다 낮아지지는 않는다. 줄어드는 폭도 일반과 비슷하다. 지금의 긴급 판정으로는 VIP 계좌를 쓰는 트랜잭션이 모두 긴급이라, 긴급은 주로 긴급끼리 충돌하기 때문이다.
- **확인되지 않은 것 (공정성):** 사용자별 실패율의 편차는 대체로 줄지만, 전체 실패가 줄어든 결과와 구분되지 않는다. 실패율 기준(3번)을 끈 것과 비교해야 따로 말할 수 있다.
- 시뮬레이션은 한 배치 안의 충돌만 본다. 스케줄링 계산 자체는 수십~수백 µs이고, 실제로 늘어나는 시간은 오더러 ↔ Kafka ↔ 프로세서 왕복이다. 이 왕복을 포함한 종단 간 비교는 하지 않았다.
