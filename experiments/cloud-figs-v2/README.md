# 클라우드 1,000 TPS s 실험 재측정 (NOTES §78)

- **조건:** §54와 같다. smallbank, 계좌 100, s 0~2 × 배치 100/500/1000 × Fabric(A1) / Serializer(ε .1/.75), 1,000 TPS, Query 50%, 사용자 5명, 긴급 0, 30초(앞 5초 제외), 3바퀴, 워커 5. 90회 모두 정상이었다(2026-10-18 16:11~18:11 KST).
- **달라진 것:** Caliper SDK 부담을 고친 상태로 쟀다(§68, `users.js installFastTxListener`).
- **결과 위치:** `bench/zipfbench/results/cloud2/cloud2-s<s>-b<B>`
- **그림 만들기:** 어제와 같은 스크립트를 `CLOUD_DIR`, `CLOUD_PREFIX=cloud2`로 돌렸다(`cloudfigs.js`, `cloudfigs2.js`, `cloudfigs3.js`, `cloudfig-choice.js`). 그림 이름은 `../cloud-figs`와 같다.
- **빠진 것:** 저충돌 점(계좌 1천·1만, §55)은 다시 재지 않아 그림 B에 없다.

## 어제(§54)와 달라진 점

| 항목 | 어제 | 재측정 |
|---|---|---|
| Serializer가 받은 TPS | 867~986 | **999~1,001** (Fabric과 같다) |
| 성공 배율 (s 1.0, 배치 100 / 500 / 1000) | ×1.21 / ×1.78 / ×2.54 | **×1.31 / ×2.10 / ×2.98** |
| 성공 배율 최대 (s 2.0, 배치 1000) | ×6.86 | **×7.93** |
| 커밋 지연 S − F (배치 100 / 500 / 1000) | +5~42 / +130~161 / +219~401 ms | **−11~−18 / −46~−82 / −130~−187 ms** (모든 조건에서 Serializer가 짧다) |
| 블록 간격 | Serializer가 2~16% 길었다 | **같다** (100 / 500 / 1,000 ms) |
| Fabric 수치 | | 어제와 1~2% 안으로 같다 |

**s 1.0 기준 상세** (3회 평균)

| 배치 | Fabric 성공/s | Serializer 성공/s | 배율 | 커밋 지연 F → S | 모든 tx 지연 차이 | Query 성공률 F / S |
|---|---|---|---|---|---|---|
| 100 | 384.1 | 502.0 | ×1.31 | 199 → 181 ms | −34 ms | 39.2 / 65.2% |
| 500 | 242.3 | 509.3 | ×2.10 | 517 → 459 ms | −84 ms | 24.4 / 81.1% |
| 1000 | 169.0 | 503.7 | ×2.98 | 930 → 787 ms | −182 ms | 16.6 / 86.1% |

**해석**
- **어제 본 "Serializer의 비용"은 측정 도구 탓이었다.** 덜 받는 TPS, 큰 배치의 지연 손해, 긴 블록 간격이 모두 그랬다.
- **이제 Serializer는 지연 손해가 없고 오히려 짧다.** 블록에서 무효가 될 tx를 빼 피어 처리가 가볍기 때문이다(블록 처리 F/S: 배치 1000에서 259/174 ms).
- **s 1.0 선택 근거(그림 7)는 더 강해졌다.** 이제는 "모든 배치에서 지연 손해 없이 ×1.3~3.0"이다.
- **사용자별 공정성도 좋아졌다.** 가장 먼 사용자 대 가까운 사용자의 비(U5/U1)가 Fabric 0.52~0.72, Serializer 0.61~0.93이다(그림 6).
