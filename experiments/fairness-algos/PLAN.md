# 다음 실험 계획: 사용자 공정성 + 다른 재정렬 알고리즘과의 비교 (NOTES §79, 초안)

## 1. 보이고 싶은 것

1. **Q1 재정렬 알고리즘 비교:** 같은 부하에서 성공 처리량, 지연, 공정성이 어떻게 다른가.
   - Serializer(ε), Fabric++(FPP), HTFabric(WARD, 재실행 없이 정렬만), 같은 소스 Fabric(A1)을 비교한다.
   - 지금까지는 로컬 250 TPS(§40)뿐이다. 클라우드 1,000 TPS에서 다시 본다.
2. **Q2 공정성:** 사용자마다 성공 기회가 고른가.
   - 늦게 도착하는 사용자(네트워크가 먼 사용자)가 불리해지는지 본다.
   - 알고리즘별로 abort가 특정 사용자에게 몰리는지 본다.
3. **Q3 Serializer의 공정성 장치:** abort 점수 e^{α·n}(사용자별 누적 abort가 적은 쪽을 버림)의 α를 바꾸면 공정성이 달라지는가. α = 0이면 공정성을 고려하지 않는다.
4. **Q4 긴급(VIP)과 공정성:** VIP를 우선할 때 일반 사용자끼리의 공정성이 유지되는가. VIP가 유리한 것은 의도된 결과이므로, 일반 사용자 4명만으로 따로 잰다.

## 4. 실험 전에 할 일

1. **FPP·HTF 동작 확인.** 메타데이터 전송(§46)과 SDK 우회(§68) 뒤로는 FPP·HTF를 클라우드에서 돌려 본 적이 없다. 짧은 사전 점검(각 1회, 약 5분)이 필요하다.
2. **α를 바꿀 수 있게 하기.** `kafka/docker-compose.processor.yml`에 `-alpha ${PROCESSOR_ALPHA:-1}`을 넣고 userbench에서 넘긴다.
3. **사용자별 abort 순서 기록.** 지금 워크로드는 사용자별 합계만 남긴다. 연속 abort(굶주림)를 보려면 tx마다 결과와 시각을 남겨야 한다(users.js, 작은 변경).
4. **공정성이 생길 원인 점검.**
   - 지금 부하에서는 사용자와 계좌가 무관하다(모든 사용자가 같은 Zipf로 계좌를 고른다). 그래서 사용자 간 차이는 ① 도착 지연(흉내)과 ② 알고리즘의 희생자 선택에서만 생긴다.
   - "인기 계좌를 많이 쓰는 사용자" 같은 차이를 보려면 사용자별로 다른 계좌 분포를 두는 옵션이 필요하다(선택).
5. **(선택) 실제 망 지연.** 사용자별 Caliper를 컨테이너로 나누고 `tc netem`을 쓴다(§61). 흉내 지연의 한계를 없애려면 필요하지만 작업이 크다.

## 5. 이미 알고 있는 것 (§32~§40, 로컬 250 TPS)

- smallbank에서 Serializer가 처리량, Query 성공률, 긴급 성공률에서 가장 높았다.
- 공정성(사용자 간 sd)은 Fabric++가 가장 좋았고, Serializer가 그다음이었다.
- custom에서는 WARD가 비슷하거나 앞섰다. ε를 1에 가깝게 두면 Serializer도 같은 수준이었다.
- 그때는 측정 도구 부담(§68)이 있었다. 지금은 고쳐졌으므로 다시 잴 가치가 있다.

## 6. 결정이 필요한 것

- 실제 망 지연(netem)까지 갈지, 아니면 흉내 지연으로 하고 한계를 밝힐지
- BE를 논문 ε 하나로만 할지, ε 1도 같이 넣을지
- 사용자별 계좌 분포 차이를 넣을지
